# معماری پیشنهادی

**وضعیت:** طرح اولیه؛ پیش از پیاده‌سازی باید با آزمون فنی تأیید شود.

## 1. اجزای منطقی
- رابط کاربری: WinUI 3 و C#؛ مسئول پنجره‌ها، فهرست و تعامل کاربر.
- لایهٔ ارتباط UI/Core: مرز مشخص، مستند و قابل آزمایش.
- هستهٔ دانلود: Rust؛ مسئول شبکه، صف، عملیات فایل و مدیریت خطا.
- ذخیره‌سازی: SQLite محلی برای وضعیت و اطلاعات لازم جهت بازیابی.

## 2. شبکه
برنامه مستقیماً به میزبان فایل متصل می‌شود. در طرح فعلی سرور اختصاصی، حساب ابری یا سرویس راه‌دور وجود ندارد. سرعت و امکان ادامه تحت تأثیر شبکه و رفتار میزبان است.

لایهٔ HTTP باید این موارد را رعایت کند:
- مدیریت هدایت‌های HTTP به‌صورت کنترل‌شده.
- مدیریت خطاهای شبکه و کدهای وضعیت.
- اعتبارسنجی TLS.
- پشتیبانی از Range فقط وقتی سرور واقعاً آن را ارائه کند.
- پاک‌سازی امن نام فایل و جلوگیری از خارج‌شدن مسیر از پوشهٔ مقصد.
- زمان انتظار و تلاش مجدد محدود.
- استفاده از ETag یا Last-Modified، در صورت موجودبودن، برای بررسی ادامهٔ دانلود.

## 3. ارتباط Rust و WinUI
گزینهٔ اولیه، ساخت کتابخانهٔ Rust با رابط C ABI و فراخوانی از C# با P/Invoke است. این روش می‌تواند نیاز به یک فرایند جداگانه را کاهش دهد، اما مدیریت حافظه، رشته‌ها، خطاها، لغو و رویدادهای پیشرفت باید دقیق طراحی شود.

قواعد:
- فقط نوع‌های ساده و قراردادهای مشخص از مرز عبور کنند؛ نوع‌های پیچیدهٔ Rust مستقیماً به C# داده نشوند.
- حافظه توسط لایهٔ تخصیص‌دهنده آزاد شود.
- panic از مرز ABI عبور نکند.
- خطاها کد و پیام مشخص داشته باشند.
- به‌روزرسانی UI روی Dispatcher مناسب انجام شود و رابط هنگام دانلود مسدود نشود.
- لغو و خاموش‌کردن تمیز از ابتدا در قرارداد درنظر گرفته شوند.

### امکان‌سنجی پیش از معماری قطعی
یک نمونهٔ کوچک باید ثابت کند که تابع Rust از C# قابل فراخوانی است، اطلاعات و خطا منتقل می‌شوند، UI پاسخ‌گو می‌ماند و لغو/بستن تمیز قابل کنترل است. اگر این مسیر شکننده یا بیش از حد پیچیده بود، گزینه‌هایی مانند ارتباط محلی میان دو فرایند بررسی می‌شوند. این بررسی در آینده است و در حال حاضر کدی نوشته نشده است.

## 4. ذخیره‌سازی محلی
SQLite می‌تواند شناسهٔ دانلود، مسیر، نام فایل، وضعیت، اندازه و پیشرفت، زمان‌ها، تعداد تلاش‌ها و اطلاعات لازم برای بررسی ادامه را ذخیره کند. فایل‌های بزرگ روی دیسک ذخیره می‌شوند، نه در پایگاه داده. وضعیت ذخیره‌شده به‌تنهایی تضمین نمی‌کند که سرور ادامه را قبول کند.

## 5. دانلود چندبخشی
این قابلیت بهینه‌سازی اختیاری است. نسخهٔ پایه باید ابتدا دریافت تک‌جریانی مطمئن و بازیابی درست را ارائه کند. تقسیم‌بندی فقط با پشتیبانی سرور انجام شود و تعداد بخش‌ها محدود باشد.

## 6. افزونهٔ مرورگر
در نسخهٔ اولیه نیست. در مرحله‌ای جداگانه می‌توان سازوکار Native Messaging را بررسی کرد. این روش ممکن است به نصب و ثبت مؤلفهٔ محلی نیاز داشته باشد، اما به معنی نیاز به سرور ابری نیست.

## 7. ترتیب پیشنهادی
1. تأیید نیازمندی‌ها.
2. ثبت مرجع تصویری UI.
3. امکان‌سنجی Rust/WinUI.
4. تعریف قرارداد API و وضعیت‌های دانلود.
5. بررسی وابستگی‌ها و مجوزها.
6. شروع پیاده‌سازی پس از تأیید مستندات.
