# معماری پیشنهادی

**وضعیت:** گزینه‌های اولیه؛ هنوز برای پیاده‌سازی تأیید نشده‌اند.

## 1. هدف تصمیم‌گیری

پروژه یک دانلودمنیجر شخصی برای Windows 11 است. مهم‌ترین معیارها عبارت‌اند از: وفاداری چیدمان و گردش‌کار IDM، پایداری دانلود، امنیت فایل‌ها، و سادگی ساخت و عیب‌یابی برای مالک مبتدی. انتخاب Rust یا یک چارچوب رابط نباید پیش از آزمون کوچک قطعی شود.

## 2. گزینه‌های هسته

### گزینه A: تماماً C#
رابط و منطق شبکه/صف در C#؛ پایگاه دادهٔ پیشنهادی SQLite.

مزیت: یک زبان، مرز بین‌زبانی کمتر و عیب‌یابی ساده‌تر. از آنجا که دانلود معمولاً منتظر شبکه و دیسک است، سرعت خام Rust الزام قطعی این محصول نیست. اگر هدف اصلی استفاده از نرم‌افزار قابل‌اعتماد با پیچیدگی کمتر باشد، این گزینه ارزش بررسی جدی دارد.

### گزینه B: رابط C# و کتابخانهٔ Rust در همان فرایند
هسته با C ABI و از طریق P/Invoke فراخوانی شود.

مزیت: بدون فرایند جداگانه.  
هزینه: مدیریت رشته، حافظه، callback، لغو، خطا و panic در مرز زبان‌ها دشوار است؛ خطای هسته می‌تواند برنامهٔ اصلی را از کار بیندازد.

### گزینه C: رابط C# و موتور Rust به‌صورت فرایند جدا
موتور Rust به‌عنوان فرایند جانبی اجرا شود و رابط از طریق Named Pipe و پیام‌های JSON با قرارداد نسخه‌بندی‌شده با آن ارتباط بگیرد.

مزیت: موتور جداگانه آزموده می‌شود و کرش آن لزوماً به‌معنی کرش UI نیست.  
هزینه: مدیریت چرخهٔ عمر فرایند، امن‌سازی کانال، پیام‌ها، نسخه‌بندی و خطاهای ارتباطی.

هیچ گزینه‌ای هنوز نهایی نیست. دلیل مالک برای ترجیح Rust (یادگیری/علاقه یا نیاز فنی) هم باید در تصمیم نهایی لحاظ شود.

## 3. چارچوب رابط: WinUI 3 در برابر WPF

هر دو گزینه با C# بررسی می‌شوند. WinUI 3 برای برنامه‌های مدرن ویندوز مناسب است؛ اما برای رابط کلاسیک و پرتراکم مرجع، جدول، تراکم کنترل‌ها، جداکنندهٔ قابل‌کشیدن و تنظیم متن فارسی باید آزمایش شوند. WPF یک گزینهٔ جدی است، به‌خصوص برای جدول پرتراکم و سبک‌دهی دقیق کنترل‌ها.

### نمونهٔ مقایسه‌ای لازم
قبل از انتخاب:
- پنجرهٔ آزمایشی با پنل گروه‌ها در چپ و جدول در راست.
- متن فارسی راست‌چین، اما ساختار کلی LTR.
- تم تیره و تراکم نزدیک IDM.
- جدول با 1,000 ردیف ساختگی، مرتب‌سازی و تغییر اندازهٔ ستون‌ها.
- جداکنندهٔ قابل‌کشیدن بین درخت و جدول.
- نام‌های فارسی، لاتین و ترکیبی.
- ثبت زمان/پیچیدگی ساخت، خطاهای RTL/Bidi، پاسخ‌گویی و میزان نیاز به کنترل‌های سفارشی.

این آزمایش فقط برای انتخاب تکنولوژی رابط است و به معنی شروع ساخت محصول کامل نیست.

## 4. اصول هستهٔ دانلود

- هر دانلود حالت مشخصی دارد: در صف، در حال اتصال، در حال دانلود، مکث‌شده، کامل، ناموفق یا لغوشده.
- یک مدیر مرکزی وضعیت و صف را نگه می‌دارد؛ UI فقط رویدادها را نمایش می‌دهد و درخواست‌ها را می‌فرستد.
- تعداد دانلودهای هم‌زمان محدود باشد.
- مکث، لغو و خاموش‌کردن تمیز از ابتدا در قرارداد عملیات لحاظ شوند.
- دانلود ناقص در فایل موقت نگهداری شود و فقط پس از تکمیل معتبر به نام نهایی منتقل شود.
- ادامهٔ دانلود فقط با پشتیبانی واقعی Range و بررسی سازگاری منبع انجام شود؛ پاسخ HTTP 206 به‌عنوان نشانهٔ پاسخ جزئی پذیرفته شود.
- اگر موجود بود، ETag یا Last-Modified هنگام ادامه بررسی شود؛ اگر منبع تغییر کرده باشد، از ادغام بخش‌های ناسازگار جلوگیری شود.
- خطاهای موقت و دائمی تفکیک شوند؛ تلاش مجدد محدود و با فاصلهٔ کنترل‌شده باشد.
- رویدادهای پیشرفت با نرخ معقول ارسال شوند تا UI قفل نشود.

## 5. شبکه، فایل و امنیت

- فقط HTTP/HTTPS در نسخهٔ اولیه پذیرفته شود؛ طرح‌های دیگر و تغییر مسیر به آن‌ها رد شوند.
- اعتبارسنجی TLS هرگز غیرفعال نشود.
- نام فایل پیشنهادی سرور پاک‌سازی شود و نتواند مسیر مقصد را دور بزند.
- فایل موجود بدون اجازه جایگزین نشود.
- فایل دانلودشده خودکار اجرا نشود.
- URL، توکن و کوکی محرمانه در لاگ ثبت نشوند.
- خطای شبکه، دیسک پر، مجوز نامجاز و پاسخ ناقص پیام واضح داشته باشد.
- چون مخزن عمومی است، هیچ دادهٔ محرمانه، log واقعی یا URL خصوصی در نمونه‌ها/مستندات ثبت نشود.

## 6. ذخیره‌سازی محلی

SQLite گزینهٔ فعلی برای شناسه، مقصد، وضعیت، اندازه/پیشرفت، زمان‌ها، شمار تلاش و اطلاعات اعتبار منبع است. فایل‌های دانلودی روی دیسک ذخیره می‌شوند، نه در دیتابیس. وضعیت دیتابیس به‌تنهایی اثبات نمی‌کند که فایل موقت با منبع سازگار است؛ هنگام بازیابی باید فایل و اطلاعات منبع تطبیق داده شوند.

جزئیات schema و سیاست تراکنش پس از تصمیم دربارهٔ مالکیت موتور و انتخاب هسته نهایی می‌شوند.
